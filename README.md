# Pantusso — Softball Team Manager

A web app for managing a recreational softball team: roster, seasons, scheduling, attendance tracking, player availability, and batting lineup management.

---

## Architecture

### Stack

| Layer | Technology |
|---|---|
| Framework | Next.js 14 (App Router) |
| Language | TypeScript |
| ORM | Drizzle ORM 0.30 |
| Database (dev) | SQLite via `better-sqlite3` |
| Database (prod) | MySQL via `mysql2` |
| Auth | NextAuth.js v4, credentials provider, JWT |
| Lineup editor | `ebbets` (local package at `../ebbets`) |
| Styling | Plain CSS (`app/globals.css`) |
| Container | Docker + docker-compose |
| CI | GitHub Actions |

### Database

The schema lives in `db/schema.ts` and is written against the SQLite column builders. At runtime, `db/index.ts` inspects `DATABASE_URL` and swaps in the appropriate Drizzle driver:

- `sqlite:./path/to/file.db` → `drizzle-orm/better-sqlite3`
- `mysql://…` or `mysql2://…` → `drizzle-orm/mysql2`

TypeScript always sees the SQLite types; the MySQL path is correct at runtime. Migrations are plain SQL files in `db/migrations/` generated by Drizzle Kit.

**Tables:**

| Table | Purpose |
|---|---|
| `users` | Admin / manager accounts |
| `players` | Roster members; each has a stable `availability_token` UUID |
| `seasons` | Named date ranges (e.g. "Spring 2026") |
| `season_roster` | Many-to-many: which players are on each season |
| `opponents` | Opposing teams |
| `games` | Scheduled, completed, or cancelled games |
| `game_players` | Per-game attendance and availability timestamps |
| `lineup_entries` | Batting order and field positions for a game |

### App structure

```
app/
  (admin)/          # Auth-gated layout (requireSession)
    layout.tsx      # Nav shell + auth guard
    seasons/        # Season list, season detail, season roster management
    roster/         # Player list, player detail/edit
    opponents/      # Opponent CRUD
    users/          # User management (admin only)
    games/[id]/     # Game detail: attendance panel + lineup editor
  availability/
    [token]/        # Public token-gated availability page (no auth)
  login/            # Credentials sign-in page
  api/              # REST endpoints (used by client components)
    auth/           # NextAuth handler
    availability/   # GET + PATCH player availability by token
    games/          # PATCH game fields; nested attendance + lineup routes
    seasons/        # Season roster + game management
    roster/         # Player CRUD
    opponents/      # Opponent CRUD
    users/          # User CRUD

components/
  NavLinks.tsx              # Client component — active nav state via usePathname
  SignOutButton.tsx         # Client component — NextAuth signOut
  lineup-editor-wrapper/    # Wraps the ebbets LineupManager:
    index.tsx               #   translates DB entries ↔ ebbets props, debounced auto-save

lib/
  auth.ts           # NextAuth authOptions (credentials provider)
  session.ts        # requireSession() / requireAdmin() helpers
  availability.ts   # Token lookup, upcoming-games query, setAttendance upsert
  games.ts          # createGameWithRoster (inserts game + seeds game_players for all rostered players)

db/
  schema.ts         # All 8 tables + relations + exported TypeScript types
  index.ts          # Driver-switching singleton
  seed.ts           # Idempotent dev seed (admin user, 12 players, season, opponents, games)
  migrations/       # SQL files generated by drizzle-kit generate
```

### Mutation pattern

Server components use **Server Actions** for form submissions (inline `async function` with `'use server'`). Client components that need optimistic updates (attendance toggling, lineup editing) call **API routes** via `fetch`.

### Auth

NextAuth credentials provider authenticates against the `users` table using bcrypt. The JWT callback embeds `id` and `role`; the session callback surfaces them on `session.user`. Two guards:

- `requireSession()` — redirects to `/login` if no session
- `requireAdmin()` — additionally redirects to `/seasons` if role is not `admin`

### Lineup editor

The `ebbets` package is a controlled React component (`LineupManager`) backed by dnd-kit. The wrapper in `components/lineup-editor-wrapper/` handles the translation layer:

- **DB → ebbets:** `lineup_entries` rows sorted by `batting_order` become the `players` array; confirmed players not in the lineup become implicit bench entries in ebbets.
- **ebbets → DB:** on every `onLineupChange` callback, the new state is translated back to `LineupEntry[]` and debounce-saved (500 ms) to `PUT /api/games/[id]/lineup`.
- `LineupManager` uses dnd-kit browser APIs so the wrapper uses `dynamic(..., { ssr: false })`.

### Player availability

Each player has a stable `availability_token` (UUID). Managers share `https://yourdomain.com/availability/<token>` with players. The public page lists upcoming scheduled games and lets players tap "I'm In" / "Can't Make It" — no account required. Tokens can be regenerated from the roster admin page.

## Local development

### Prerequisites

- Node.js 20+
- npm

### Setup

```bash
# Install dependencies (ebbets is resolved from ../ebbets — must be built first)
npm install

# Copy and edit environment variables
cp .env.example .env

# Apply migrations and seed the database
npm run db:migrate
npm run db:seed

# Start the dev server
npm run dev
```

Open `http://localhost:3000` and sign in with the credentials from your `.env` (`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`).

### Environment variables

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | Yes | `sqlite:./dev.db` for local; `mysql://user:pass@host:3306/db` for prod |
| `NEXTAUTH_SECRET` | Yes | Random string used to sign JWTs — generate with `openssl rand -base64 32` |
| `NEXTAUTH_URL` | Yes | Full base URL of the app (e.g. `http://localhost:3000`) |
| `SEED_ADMIN_NAME` | Seed only | Display name for the initial admin account |
| `SEED_ADMIN_EMAIL` | Seed only | Email for the initial admin account |
| `SEED_ADMIN_PASSWORD` | Seed only | Plaintext password — hashed at seed time, not stored |

### Docker (local)

```bash
cd docker
docker compose up --build
```

This builds the app inside Docker and runs `npm run dev` against a volume-mounted source tree. The SQLite database is persisted in the `db-data` Docker volume.

## Scripts

| Script | Command | Description |
|---|---|---|
| `dev` | `next dev` | Start Next.js development server with hot reload |
| `build` | `next build` | Production build (outputs to `.next/standalone`) |
| `start` | `next start` | Serve the production build locally |
| `lint` | `next lint` | ESLint via `eslint-config-next` |
| `typecheck` | `tsc --noEmit` | TypeScript type check without emitting files |
| `test` | `vitest` | Run the Vitest test suite |
| `db:generate` | `drizzle-kit generate` | Diff `db/schema.ts` against existing migrations and generate a new SQL migration file |
| `db:migrate` | `drizzle-kit migrate` | Apply all pending migrations to the database pointed to by `DATABASE_URL` |
| `db:seed` | `tsx db/seed.ts` | Idempotent seed: creates the admin user, 12 sample players, a season, opponents, and games. Safe to re-run. |

## Deployment

### Target: Digital Ocean Droplet + Nginx + MySQL

#### 1. Provision

- Droplet: Ubuntu 22.04, 2 GB RAM minimum
- Managed MySQL database (or self-hosted)
- Point your domain's A record at the droplet IP

#### 2. Build and push the Docker image

```bash
# From the project root
docker build -f docker/Dockerfile -t ghcr.io/<org>/pantusso:latest .
docker push ghcr.io/<org>/pantusso:latest
```

GitHub Actions (`.github/workflows/`) builds and pushes on every merge to `main`.

#### 3. Configure the server

Create `/opt/pantusso/.env` on the droplet:

```env
DATABASE_URL=mysql://user:password@your-mysql-host:3306/pantusso
NEXTAUTH_SECRET=<openssl rand -base64 32>
NEXTAUTH_URL=https://yourdomain.com
```

#### 4. Run the container

```bash
docker run -d \
  --name pantusso \
  --restart unless-stopped \
  --env-file /opt/pantusso/.env \
  -p 3000:3000 \
  ghcr.io/<org>/pantusso:latest
```

On startup the container runs `node scripts/migrate.js` to apply any pending migrations before starting the Next.js server.

For the initial deploy, run the seed script once to create the admin account:

```bash
docker run --rm --env-file /opt/pantusso/.env \
  -e SEED_ADMIN_NAME="Your Name" \
  -e SEED_ADMIN_EMAIL="you@example.com" \
  -e SEED_ADMIN_PASSWORD="<strong-password>" \
  ghcr.io/<org>/pantusso:latest \
  node -e "require('tsx/cjs'); require('./db/seed.ts')"
```

#### 5. Nginx reverse proxy

```nginx
server {
    listen 80;
    server_name yourdomain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name yourdomain.com;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection 'upgrade';
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_cache_bypass $http_upgrade;
    }
}
```

Use Certbot to obtain the TLS certificate:

```bash
certbot --nginx -d yourdomain.com
```

#### 6. Schema changes

After deploying a new image that contains new migrations, the container's startup command (`node scripts/migrate.js`) applies them automatically before the server starts.
